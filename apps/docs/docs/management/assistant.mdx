# Assistant

Assistant answers questions and operates Homarr through the signed-in user's permissions. Read-only tools can run
automatically; changes require approval by default.

## Configuration

Under **Management → Assistant**, select a provider, configure its API URL and key when required, select the default
model, and enable Assistant. Users can choose another available model for a conversation.

Provider presets cover common APIs. **Custom endpoint** accepts an OpenAI-compatible Chat Completions API. For a model
server outside the Homarr container, use a hostname that the container can resolve instead of `localhost`.

The [Homarr provider](/docs/workshop/homarr-provider) is available through the Community Workshop without an administrator
API key and has a daily request allowance.

<Alert type="warning" title="Using an existing AI subscription">

Homarr Assistant cannot use existing AI subscriptions such as Claude or GitHub Copilot, and this is not planned. To use
your preferred AI client with Homarr, connect it to the [Homarr MCP server](/docs/management/mcp).

</Alert>

### Custom endpoint user identity

To identify Assistant users at a Custom endpoint, enable
[signed identity assertions](/docs/advanced/environment-variables#assistant-identity). Homarr keeps a dedicated Ed25519
private key; give the endpoint only the corresponding public key through a trusted channel. The endpoint API key
continues to authenticate access to the endpoint separately.

When enabled, each chat completion request carries `X-Homarr-User-Assertion`, an EdDSA-signed JWT valid for 60 seconds,
and `X-Homarr-User-Id`, the authenticated user's immutable Homarr database ID. Renaming a user does not change this ID.
Homarr generates a fresh assertion for every outbound request, including retries and tool follow-ups. Assertions are
not generated for model discovery or other provider presets. Both headers are reserved in Custom endpoint chat
requests, regardless of casing; without signing configured, neither header is sent.

The JWT uses `typ: homarr-assistant-identity+jwt` and these claims:

| Claim               | Meaning                                                           |
| ------------------- | ----------------------------------------------------------------- |
| `iss`, `aud`        | Configured Homarr issuer and endpoint audience                    |
| `sub`               | Authenticated Homarr user ID                                      |
| `iat`, `nbf`, `exp` | Issue time, earliest acceptance time, and expiry, in Unix seconds |
| `jti`               | Unique ID for this outbound request                               |
| `htm`, `htu`        | HTTP method (`POST`) and exact configured chat completion URL     |
| `body_sha256`       | Base64url-encoded SHA-256 of the exact HTTP request body bytes    |

The endpoint must verify the signature with the pinned public key, allow only `EdDSA`, and require the expected type,
issuer, audience, subject, and time claims with a maximum lifetime of 60 seconds. It must also compare `htm`, `htu`,
and `body_sha256` with the received request, require `X-Homarr-User-Id` to equal the verified `sub`, and atomically reject
reused `(iss, jti)` values until expiry. Allow only a small clock tolerance, and retain replay entries for that tolerance
as well. If a proxy rewrites the URL, compare `htu` against the trusted external endpoint URL configured in Homarr.
Hash the body before parsing or rewriting it. Reject missing or invalid assertions instead of falling back to the
unsigned user ID or endpoint bearer token. Signed requests do not follow redirects.

Use HTTPS for remote connections. Scope account mappings to the verified `(iss, sub)` pair; the endpoint remains
responsible for pairing and per-user permissions. The private signing key must remain separate from the endpoint
API key and must never be shared with other clients.

## Access

Open Assistant from the user menu, with `Shift+A`, from search with `Cmd/Ctrl+/`, or through the
[Assistant widget](/docs/widgets/assistant).

Homarr checks Assistant availability alongside other page settings, so an enabled Assistant appears with the dashboard
without reloading its widgets after the page opens. Widget configuration loads its editor when you open the configuration
dialog.

Assistant can work with boards, apps, integrations, widgets, Custom Widgets, and supported connected services. Mention
Homarr resources with `@`; the model loads additional live context only when needed.

Conversations are stored per user and can be searched, renamed, exported, or deleted.

## Permissions and data

- Every tool call uses the current user's Homarr permissions.
- Automatic approvals apply only to the current conversation and reset when switching conversations.
- Provider keys and custom headers are encrypted and are not returned to the browser.
- Prompts, attachments, tool definitions, and tool results are sent to the selected model provider.

See [MCP](/docs/management/mcp) to connect an external AI client and
[Custom Widget agent authoring](/docs/management/custom-widgets/agent-authoring) for widget generation.

## Troubleshooting

- **No models found:** check the API URL, discovery path, and API key, or enter a model ID manually.
- **Assistant is unavailable:** enable it and save the configuration.
- **Tool calls stop:** use a model that supports streaming and tool calls.
- **Local endpoint is unreachable:** check container DNS, routing, and the model server's listen address.
